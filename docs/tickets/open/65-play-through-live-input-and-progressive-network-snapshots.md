# Play through live input and progressive network snapshots

The current remote client sends a precomputed input trace and renders only its final received snapshot, while the dedicated server binds only to localhost. Let two live clients send controls during play and render progressive authority snapshots, with a client-host using the same dedicated-authority loop and transport boundary.

## Outcome

- Supported dedicated, join and host commands run bounded direct-IP development sessions. The dedicated bind defaults to loopback; a nonlocal address must be explicit. A host runs the same live authority loop on a joined thread and its own player connects over its own UDP socket to the bound address, using loopback when that bind permits it, exactly like the remote peer. The client socket supports reaching the explicitly selected IPv4 endpoint.
- The authority owns a 60 Hz clock, applies each peer's newest held controls through the existing AuthoritativeMatch step, and emits snapshots without waiting for one input from each peer every tick. Late processing never creates burst catch-up steps. Existing unpaced scripted smoke/replay/capture routes and their 6,000-tick cap remain supported; live sessions accept positive bounds through 36,060 ticks, enough for either complete supplied recording.
- Each client renders the latest validated received MatchSnapshot through the shared Bevy scene. Its network presenter constructs no AuthoritativeMatch, predicts no transforms and applies no game rules. Keyboard/gamepad mappings and programmatic drivers submit the same public PlayerInput and semantic flow commands for their assigned slot.
- Flow commands preserve FIFO order with stable edge identities. The authority consumes an edge once and acknowledges consumption even when game rules reject it as stale, duplicate or wrong-phase. Held controls continue updating while an edge awaits acknowledgement. Fast commands constructed from an old displayed snapshot may be rejected by existing game rules; they cannot pick a different item or replay forever.
- Normal client completion requires a hash-validated final authoritative state. The authority reports which peers acknowledged terminal delivery, distinguishing simulation completion from unconfirmed delivery. Close, peer loss, validation failure, join failure and terminal-packet loss produce named non-success results within explicit bounds. Every client network thread, host authority thread and launched child is joined or exited; sockets can be rebound after termination.
